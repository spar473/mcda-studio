# Architecture overview

MCDA Studio has three parts:

- a Python package, `mcda_studio`, which does all the mathematics;
- a thin FastAPI layer;
- a React/TypeScript frontend that never calculates.

## Repository layout

| Path | Contents |
| --- | --- |
| `src/mcda_studio/domain/` | Pydantic models and structural validation |
| `src/mcda_studio/methods/` | The method registry; `mavt/` holds value functions, weighting, aggregation, sensitivity and previews; `sorting/` sorts MAVT values into ordered classes; `smaa/` samples stated uncertainty for acceptabilities; `promethee/` computes outranking flows and the explanation against MAVT; `ahp/` derives priorities and consistency from pairwise judgements |
| `src/mcda_studio/services/` | Immutable editing, analysis entry points, scenario/profile operations, analysis records and exports |
| `src/mcda_studio/storage/` | JSON repository, project library store, fingerprints and ETags |
| `src/mcda_studio/api/` | FastAPI app, request schemas, edit operations and error envelope |
| `src/mcda_studio/cli.py` | The `mcda` command line |
| `frontend/src/` | React app: `components/`, `state/` (store and analysis hooks), `model/` (pure helpers), `api/` (client and generated types) |
| `tests/` | Python unit, API, integration, property and regression tests |
| `frontend/tests/`, `frontend/e2e/` | Vitest component/unit tests and Playwright browser tests |
| `examples/` | Reference projects, each generated by its own `build.py` |
| `scripts/` | Acceptance demo, evidence and timing script, mutation harness, OpenAPI export, fixture builder |

## Layers and the dependency rule

```
cli.py ──► services ──► methods ──► domain
              │                       ▲
              └──────► storage ───────┘
```

Dependencies point **down only**. `domain` imports nothing else from the package.

| Layer | Responsibility | Must not |
| --- | --- | --- |
| `domain/` | Pydantic models for projects, alternatives, criteria tree, scales, value-function *specifications*, measurements, weight profiles, scenarios, results; model-completeness validation | know which MCDA method will run |
| `methods/` | Mathematics of one technique. `methods/base.py` defines the `Method` protocol and registry; `methods/mavt/` implements value functions, weighting, aggregation, sensitivity | read or write files |
| `services/` | `project_service` (editing), `templates`, `analysis_service` (single entry point) | contain maths |
| `storage/` | Versioned JSON load/save, migrations, atomic writes | calculate anything |

The FastAPI layer sits beside `cli.py` and calls services. React sends immutable edit operations,
scoped previews and completed-record requests through the API. **The frontend never
re-implements a calculation.**

## Core decisions

* **Stable ids, never names or positions.** Every alternative, criterion, weight profile and
  scenario has an `Id`. Renaming cannot corrupt measurements.
* **Arbitrary-depth tree.** `parent_id=None` nodes are children of an implicit root. A node is a
  leaf iff nothing names it as parent. Only leaves carry a scale, value function and
  measurements (enforced by validation: `LEAF_DATA_ON_PARENT`).
* **Specification vs evaluation.** A `ValueFunctionSpec` is data (`linear`, `piecewise_linear`,
  `qualitative`, `direct_rating`). `methods/mavt/value_functions.py` turns a spec plus a resolved
  `Domain` into a pure function. The same spec evaluates the same way every time.
* **Global vs local scales are an explicit choice** (`Scale.anchor_mode`). `fixed` anchors never
  depend on the alternatives. `local` anchors are derived from them, are recorded in the result
  (`resolved_domains`), and always produce a `LOCAL_ANCHORS` warning, including when a *scenario
  override* (not the base model) is what makes a criterion local. Local anchors whose spread is at
  floating-point noise level relative to their magnitude (`<= 1e-9`) also raise
  `NEAR_DEGENERATE_LOCAL_ANCHORS`; identical min and max is the hard error
  `DEGENERATE_LOCAL_ANCHORS`.
* **Weights are always derived.** Users supply raw swing ratings per node; local and global
  weights are computed. Nobody types a global leaf weight.
* **Validation returns a report; evaluation refuses an invalid model.** Blank or half-built
  projects can be saved and reopened; they just cannot be evaluated.
* **Immutability.** Every editing function returns a new `Project`. A saved baseline or a
  template cannot be altered by editing a derived project.
* **Provenance.** Every result carries the project id, a SHA-256 fingerprint of the exact project
  evaluated, the configuration, the weight profile and scenario used, assumptions and diagnostics.
* **Scenarios** (named weight-profile and/or value-function overrides) are first-class so that
  value-function comparisons need no copies of the project.

## Extending with another method

The [method seam](../design/method-seam.md) defines the contract:

1. Add `methods/<name>/` with a parameters model (parsed from `AnalysisConfiguration.parameters`
   and checked with `check_parameters`) and a result model deriving from `AnalysisResult` with its
   own `method` tag; add it to `AnalysisResultUnion` so `/evaluate` can return it.
2. Implement the `Method` protocol (`name`, `label`, `capabilities`, `validate`, `evaluate`) and
   call `register(...)` in `methods/__init__.py`. `validate_analysis` runs the method-independent
   checks and then the method's own `validate`.
3. Declare only the capabilities the method really offers. Every capability-gated service call
   refuses the others with `METHOD_NOT_SUPPORTED`; version-1 analysis records are MAVT only.
4. Add method-specific inputs to `domain` **only** if they are method-independent facts about the
   problem; otherwise keep them in the method's own section or parameters. AHP pairwise matrices
   and PROMETHEE preference functions must not be forced into MAVT's value-function model. A new
   section is optional, omitted when absent, and raises the written schema version only for
   projects that use it (`SECTION_VERSIONS` in `domain/project.py`).
5. Give the method a version-2 analysis record (`RecordEnvelopeV2` plus its result and context),
   register its builder in `VERSION_2_RECORDS` and declare its CSV tables in `EXPORT_TABLES`
   (`services/results_service.py`). Version-1 records stay MAVT only.
6. In the frontend, register its Results panels in `components/results/panels.ts`; panels whose
   capability the method lacks are hidden. Method-specific editors appear only when the viewed
   method uses them.

**SMAA-2** (`smaa2`) is the second: it reuses MAVT's validation, evaluators and weighting per
draw, adds the `smaa` section (schema version 3), `SmaaResult`, a version-2 record with three CSV
tables, the Acceptability panel and the Uncertainty editor, and declares only `value_functions`,
`swing_weights` and `acceptability`, so sensitivity and scenario comparison refuse it.

**PROMETHEE II** (`promethee2`) is the third, and the first that does not read the MAVT model: it
runs only the method-independent measurement checks (`validate_measurements`) and its own section
rules, adds the `promethee` section (schema version 4), `PrometheeResult`, a version-2 record with
four CSV tables, the Flows, PROMETHEE I and Explanation panels and the Outranking editor, and
declares only `flows`, so sensitivity, scenario comparison and the previews refuse it. Its
explanation calls the MAVT engine unchanged and compares orders only. While it is viewed, the
frontend requests the MAVT editors' previews for `mavt`, because those editors edit the MAVT model.

**AHP** (`ahp`) is the fourth: it runs only the structural checks (`validate_structure`) and its
section rules, adds the `ahp` section (schema version 5), `AhpResult`, a version-2 record with four
CSV tables, a read-only `POST /api/ahp/preview` for one drafted matrix, the Pairwise editor and the
AHP priorities and Consistency panels, and declares only `consistency`. It reads no measurements,
value functions, profiles or scenarios, so its results name neither profile nor scenario.

**The method comparison view** (`services/comparison_service.py`) is not a method: it runs each
registered method through its own record builder, unchanged, and lays the results side by side.
A method that fails becomes a column with its typed error; agreement compares leaders and classes
only, and reasons come from each method's own result. No number combines two methods.

**The feasibility check** (`services/feasibility_service.py`) is not a method either: it tests each
alternative's measurements against the project's optional `requirements` (schema version 6) and
returns pass, fail or unknown with reasons. It reads no weights, profiles, value functions,
scenarios or method sections, and no method reads requirements, so no result, record or export of
any method changes. The GUI and CLI show its result beside every ranking.

**Value-based sorting** (`mavt_sorting`) is the first method built this way: it reuses MAVT's
validation, values and panels, adds the `sorting` section, a `MavtSortingResult`, class changes in
sensitivity, a version-2 record, a `classes` CSV table and the Classes panel and editor.


## Application integration

### Frontend state

- **`EditorStore`** owns a queued draft, session-only undo/redo and conflict-aware explicit saves.
- **The shared [analysis context](../design/analysis-context.md)** keeps explicit Base/profile
  selection separate from the project's saved defaults.
- **`useAnalysisRequest`** cancels obsolete calls and only accepts output whose key matches the
  current context.
- **Inputs.** [Previews](../design/previews.md) resolve only the inputs they need, while results
  and exports require a complete, valid effective model.

### Analysis records and exports

- **`AnalysisRecord`** wraps `MavtResult` with provenance, context, diagnostic relationships and
  export metadata. None of this is saved in the project.
- **Exports** re-evaluate a captured snapshot and verify its revision and digest before returning a
  file. There is no result cache.

### Who calculates what

| Python calculates | React does only |
| --- | --- |
| Preference values, weights and branch shares | Presentation geometry |
| Ranks, contributions and sensitivity roots | Formatting |
| Dominance | Joining rows by stable ID |
