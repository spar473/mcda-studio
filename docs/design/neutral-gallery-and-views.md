# Neutral gallery, Analyst view and wording

**Status:** Accepted by the owner, 18 November 2026, in chat (every recommended decision). Direction chosen by the owner in chat on 18 November 2026
("Re-frame + exemplars"). It comes after the three [method exemplars](method-exemplars.md), so it
lists only starters that exist. **Implemented and locally verified 19 November 2026** (development record, not included). Frontend text and ordering only:
no engine, schema, route or pinned output changes.

The application opens on venture content and speaks in venture words. For a study of inspection
vehicles or flood defences that is wrong: the detail drawer would be titled "Company detail" and
the profile comparison would say "Compare partners". This note neutralises the order, the Analyst
view default and the visible wording.

## What exists today

Read from the source at `da4bd2a`, 18 November 2026:

- **Order and labels.** `frontend/src/components/Dashboard.tsx` sets `STARTER_ORDER` to blank,
  `venture_screening_study`, `supplier_selection`, `infrastructure_procurement`,
  `venture_screening`, with a tagline and an icon path per id. An id without an icon falls back to
  the blank starter's plus sign.
- **Analyst view.** `frontend/src/state/viewMode.ts` holds one constant, `studyTemplate =
  "venture_screening_study"`. Only a project made from a worked-example starter with that id opens
  in the Analyst view automatically; any other project opens in the view the user last chose,
  which defaults to Builder. The hint lives in `sessionStorage` and never in the project.
- **Visible "company" wording.** The alternative drawer and its neighbours say "Company detail",
  "Close company detail", "Loading company detail…", "Company requirements" and "Company
  contributions", and the what-if note says "Company…" (`CompanyExplorer.tsx`,
  `EditorScreen.tsx`).
- **Visible "partner" wording.** `ResultsPanel.tsx` says "Compare partners" and "Two weight
  profiles are needed to compare partners."; `PartnerComparison.tsx` says "Partner comparison",
  "MAVT partner comparison", "Calculating partner comparison…" and names tables "Partner
  rankings…"; `useProfileComparison.ts` has error messages that begin "Partner comparison".
- **Not affected.** The Python engine and API carry no such wording, and `ExportCharts.tsx` (pinned)
  has none either: its one match is the word "accompany". **One engine-generated string does:** the
  screening report's heading `<h2>Partner comparison</h2>`
  (`src/mcda_studio/services/screening_report_service.py`). This note first said the Python side was
  clean; I had read only the first five matches of a search. See the implementation notes.
- **Tests that assert on the old words:** 13 frontend unit-test files and 8 browser specs contain
  "company" or "partner" (a case-insensitive file count; some are fixtures, so the exact assertion
  count is for the implementation to list).

## Goals and non-goals

**Goals:**

- The gallery leads with general starters, and the venture starters come last.
- Every worked-example starter that suits the Analyst view opens in it, not only the venture study.
- Visible wording is neutral: "company" becomes "alternative" and "partner" becomes "profile".
- Nothing else changes: the same screens, the same data, the same results.

**Non-goals (excluded):**

- Renaming components, files, CSS classes or `data-*` attributes (`CompanyExplorer`,
  `PartnerComparison`, `partner-toggle`). They are invisible; renaming them is a large diff for no
  user benefit.
- Any schema, route, engine text or export change. `ExportCharts.tsx`, the client SVG fixtures and
  the screening-summary fixture rules stay exactly as they are.
- Changing the words in the venture studies' own data (company names, profile names, rubric and
  evidence text). That is data, not interface wording.
- Group headings in the gallery (decision 1), new tabs, and any change to what the Analyst view
  shows. Rewriting dated verification records.
- **The screening report's "Partner comparison" heading.** It is generated by Python and pinned by
  two golden HTML fixtures and a reference test, so changing it needs the owner's approval; it is
  left as it is (see the implementation notes).

## Design

### 1. Order, taglines and icons

`STARTER_ORDER` becomes: `blank`, `supplier_selection`, `infrastructure_procurement`,
`clinic_site_selection`, `flood_defence_options`, `engineering_trade_study`,
`venture_screening_study`, `venture_screening`. An id not in the list still sorts after the listed
ones, in the gallery's own order, as today.

New taglines, one line each: "Pairwise judgements and swing weights" (clinic), "A hard requirement
and outranking flows" (flood defence) and "Every method on one model" (trade study). Each gets a
small decorative icon path, because the fallback is a plus sign that would read as "blank".

### 2. The Analyst view for a set of starters

`studyTemplate` becomes `ANALYST_STARTERS`, a frontend constant holding the four worked-example ids
(the three exemplars and `venture_screening_study`). `viewIntent` and `rememberWorkedEntry` test
membership instead of equality.

- A stored hint is accepted only when its project id matches, its fingerprint is a string and its
  starter id is in the set. The stored starter id is kept, not replaced by one constant.
- A hint for an id outside the set is ignored; the saved explicit choice, or Builder, applies.
- A corrupt value, or unavailable storage, gives Builder, as today.
- A `fresh` starter is never remembered, as today.
- Nothing touches project bytes, fingerprint, ETag, dirty state or undo history. The hint stays in
  `sessionStorage`.

### 3. Neutral visible wording

| Now | Becomes |
| --- | --- |
| "Company detail", "Close company detail", "Loading company detail…" | "Alternative detail", "Close alternative detail", "Loading alternative detail…" |
| aria-labels "Company requirements", "Company contributions" | "Alternative requirements", "Alternative contributions" |
| "Compare partners" and "Two weight profiles are needed to compare partners." | "Compare profiles" and "…to compare profiles." |
| "Partner comparison", "MAVT partner comparison", "Calculating partner comparison…", "Partner rankings…" | "Profile comparison", "MAVT profile comparison", "Calculating profile comparison…", "Profile rankings…" |
| Error messages beginning "Partner comparison" in `useProfileComparison.ts` | "Profile comparison …" |
| The what-if note's "Company…" | the matching "Alternative…" wording |

The rule is the table: visible text, aria-labels and error messages change; identifiers, file names,
CSS classes and `data-*` attributes do not. The exact list comes from a case-insensitive census of
`compan|partner` in `frontend/src` outside `api/`, and goes in the verification record. If a visible
string names a venture idea with no neutral equivalent, I stop and ask.

Living documents that name the tab or the drawer follow: `README.md`, `docs/user-guide.md` and
`docs/vc-demo-walkthrough.md`. Dated verification records are never rewritten. Screenshots in
`docs/images/` show the old words until they are retaken (the public tree retakes them).

### 4. Edge cases

- Screen-reader names change with the labels, so tests that select by role and name are updated to
  the new text, and kept at least as strict.
- An existing browser session keeps its saved view choice (same storage keys).
- The "Compare profiles" panel still needs two weight profiles and still shows its message with one.

- **Mutants** in the frontend group of `scripts/mutation_check.py`: Analyst auto-open for every
  starter; the fingerprint check dropped; the membership test inverted; blank not first; and the old

- **The full gate**, the 969-output hash, the `ExportCharts.tsx` SHA-256, and a dated record
  `docs/development/neutral-gallery-and-views-verification.md`.

## Decisions

1. **Order only, no group headings.** *Recommended:* ordering already leads with general starters
   and adds no layout. *Alternative:* headings "General examples" and "Venture studies".
2. **All four worked-example starters open in the Analyst view.** *Recommended.* *Alternative:* only
   the trade study and the venture study.
3. **Rename the visible words** as the table says. *Recommended.* *Alternative:* leave them; the
   drawer would then read "Company detail" for an inspection vehicle, which I do not recommend.
4. **Leave identifiers, file names and CSS classes alone.** *Recommended.* *Alternative:* rename them
   too, a much larger diff with no visible effect.
5. **Add three decorative starter icons.** *Recommended.* *Alternative:* accept the plus-sign
   fallback.

## Implementation notes

Built as designed, with the five decisions as recommended. What the build found:

- **The census found about thirty visible strings in five source files:** the alternative drawer
  (`CompanyExplorer.tsx`, thirteen), the what-if note (`EditorScreen.tsx`), the Results toggle and its
  message (`ResultsPanel.tsx`), the profile comparison (`PartnerComparison.tsx`: its headings, labels,
  buttons, a table header and two sentences of explanatory text that also said "company") and four
  error messages (`useProfileComparison.ts`). Eight test files (three unit, five browser) that
  assert on the old text were updated to the new text and kept at least as strict; a new unit-test
  file and new cases in three others cover the order, the icons, the Analyst set and the neutral
  words. A check found no visible string left in the
  source; the three matches that remain are a variable and the alternative's own name.
- **The Analyst-view set is `ANALYST_STARTERS`,** exported from `viewMode.ts`. A stored hint is
  accepted only for a listed starter and a string fingerprint, and the starter id it stores is the
  one that made it. A first mutant showed `rememberWorkedEntry` would store a hint for an unlisted
  starter without any visible effect, because `viewIntent` ignores it; the test now asserts nothing
  is stored for an unlisted or fresh starter.
- **A correction to this note.** The Python side is not clean: the generated screening report has a
  "Partner comparison" heading, pinned by `tests/fixtures/screening_report_nz_venture_screening.html`,
  `tests/fixtures/screening_report_supplier_qualification.html` and
  `tests/regression/test_screening_report_reference.py`. My rename changed the browser spec's
  expectation of that heading too, and the spec failed against the unchanged report; I restored the
  spec. Renaming the heading is a small change (one string, two fixture lines, one test), but it
  changes pinned goldens, so it waits for the owner (decision 6 below).
- **Screenshots in `docs/images/` still show the old words;** the README says so.
