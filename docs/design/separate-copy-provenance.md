# Separate-copy provenance

Evidence compilation and calculation bundles record the exact fingerprint of the project they
produced. `Project.fingerprint()` hashes the whole canonical model, including its `id`. A compiled
copy keeps its source project's ID, so importing it beside the original needs a separate copy, and
`import?on_conflict=new_id` replaces the ID. The imported copy therefore has a different
fingerprint from the one its artifact recorded.

That difference is kept. Fingerprints are never compared loosely, artifacts are never rebound to a
new project, and similar measurements are never treated as proof of origin.

## Copy receipt (version 1)

When an import stores a project under a new ID, the response includes a `ProjectCopyReceipt`:

| Field | Meaning |
| --- | --- |
| `transformation` | `new_project_id`: exactly one change, the `id` |
| `original_project_id`, `original_fingerprint` | The imported file's identity |
| `copy_project_id`, `copy_fingerprint` | The stored copy's identity, as first stored |
| `digest` | SHA-256 over the other fields; detects accidental changes, not deliberate rewriting |

Verification re-applies the transformation in reverse: the copy's ID is restored to the recorded
original ID, and the resulting fingerprint must equal `original_fingerprint` exactly. The copy's
current ID and fingerprint must also match the receipt. Any other difference, such as a title
change, is refused. Receipts are issued only by the project import route. Duplicating a project in
the library changes its title too, so it is not a provenance relationship.

The Projects screen offers the receipt as a download after Import as a separate copy. Keep it
with the bundle. Without it, the copy is reported as `different`.

## Artifact binding

`provenance_service.bind` verifies an artifact in full (digest, replay where applicable, complete
reconstruction), then classifies the current project:

| Relationship | Rule | Allowed |
| --- | --- | --- |
| `compiled` | Current fingerprint equals the artifact's compiled fingerprint | Historical inspection; later decision records may cite it |
| `source` | Current fingerprint equals the artifact's original project | Continue reviewing (evidence) or recalculating |
| `verified_copy` | A valid receipt relates the compiled fingerprint to the current project | As `compiled`, citing both fingerprints and the receipt |
| `different` | Anything else | Historical inspection only |

A later edit to the copy changes its fingerprint, so its receipt no longer applies and the binding
request is refused. The artifact remains readable. Review actions still require the dossier's own
project, because the existing preview reports a stale dossier for any other fingerprint. Chains
of copies (a copy of a copy) need one receipt per import and are not combined automatically.

## Limits

- Receipts and bundle digests are unsigned local checksums. They do not authenticate who imported,
  reviewed or compiled anything, and do not establish that evidence or calculations are accurate.
- A receipt that is not downloaded at import time cannot be regenerated by the application. The
  bundle and project still verify individually, but their relationship is then reported as
  `different`.
- No project schema field, library sidecar or migration was added. Receipts live beside the
  user's exported artifacts.
