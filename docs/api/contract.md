# HTTP API contract

The HTTP API is a thin layer over the Python domain, services and storage. **It contains no
mathematics and no editing rules.**

- Every request and response body is a domain model.
- Every edit goes through `services/project_service`.
- Analysis goes through `services/analysis_service`, and completed records and exports through
  `services/results_service`.

The project schema ([`project_schema.json`](../architecture/project_schema.json)) is the single
source of truth. The API's `Project` body has exactly the same properties, and a test asserts it.

**References:**

- **Machine-readable contract:** [`openapi.json`](openapi.json), generated by
  `python scripts/export_openapi.py`. `--check` fails if it is stale, and a test runs that check.
- **Frontend types:** the TypeScript types are generated from it with `npm run gen:types`.
  `npm run check:types` fails if they are stale.
- **Interactive docs:** while the server runs, at `http://127.0.0.1:8765/docs`.
- **Conventions:** all paths are under `/api`. JSON in, JSON out, UTF-8.

## Design rules

Local evidence endpoints are stateless and do not access or write library paths:

- `POST /api/evidence/inspect` takes `{project, document}` where `document` is a version-1 dossier
  or review workspace. Returns the reconstructed current dossier, workspace, existing evidence
  preview, current measurement support and availability/exportability flags.
- `POST /api/evidence/review` takes `{project, workspace, event, expected_review_digest}`. An event
  names one claim and its explicit `Review`. Returns a candidate inspection with an appended
  review; the client confirms it in its session. Changed history is 409 `EDIT_REFUSED`; a stale
  project/preview is 412 `STALE_REVISION`; invalid acceptance is 422 `VALIDATION_FAILED`.

- `POST /api/evidence/compile` takes `{project, workspace, expected_review_digest,
  expected_workspace_digest}`. It replays the history, requires both digests to match what the
  client acknowledged, and calls the existing all-or-nothing `evidence_service.compile_copy`.
  Returns a version-1 `EvidenceCompilation`: the workspace (original project, original dossier,
  appended reviews), the exact preview, the compiled project, its fingerprint and a digest. A stale
  preview or history is 412; invalid or conflicting acceptance is 422; changed history is 409.
- `POST /api/evidence/compilation/inspect` takes `{project, bundle}`. The bundle must pass digest
  verification, replay and complete reconstruction (409 `EDIT_REFUSED` otherwise). Returns the
  verified `compilation` plus the ordinary `inspection` of its history against the current project,
  so a changed project is reported stale rather than rebound.
- `POST /api/provenance/binding` takes `{project, artifact, copy_receipt?}` where `artifact` is an
  evidence compilation or calculation bundle. After verifying the artifact it reports
  `relationship`: `compiled` or `source` (exact fingerprint equality), `verified_copy` (only with a
  valid receipt starting from the compiled fingerprint) or `different`. A tampered, inapplicable or
  outdated receipt is 409. Different fingerprints never compare equal.

- `POST /api/decisions/preview` takes `{project, details, artifacts?, predecessor?}` and returns a
  version-2 decision record built in memory (nothing is stored). `artifacts` lists
  `{artifact, copy_receipt?}`; each must anchor by exact fingerprints. `predecessor` is a version-1
  or version-2 record object, validated by the endpoint (422 `INVALID_DECISION_RECORD`), because
  records embed analysis records that are response-only models in this contract.
- `POST /api/decisions/inspect` takes `{project, record, predecessor?}` and verifies a version-1
  or version-2 record. It returns the record, whether it records exactly the open project, and
  `predecessor_verified` when a predecessor file was supplied. Unknown considered or selected
  alternatives and inconsistent analysis snapshots (missing, substituted or mislabelled) are 422
  `VALIDATION_FAILED` with explicit codes in the details, on preview and inspection alike. Changed
  or irreproducible records, unrelated artifacts and mismatched predecessors are 409 `EDIT_REFUSED`.

The [workspace design](../design/evidence-workspace.md) defines preservation and export semantics;
[decision records](../design/decision-records.md) define version-2 records;
[separate-copy provenance](../design/separate-copy-provenance.md) defines receipts and binding.
These endpoints never save a project or touch the library. Generated OpenAPI declares their models.

`POST /api/derived/preview` accepts a deterministic model or calculation bundle as `model`, with
the current `project`. A bundle must pass digest verification and complete reconstruction before
previewing. `POST /api/derived/compile` takes `{project, model, expected_review_digest}` and returns
a version-1 calculation bundle with original project/preview/model, compiled project and digests.
It calls the existing all-or-nothing compilation service and does not save or replace library
files. A stale preview returns 412; invalid calculations return 422; a changed or irreproducible
bundle returns 409. Both endpoints preserve the project schema and existing numerical engines.

The [calculation workspace](../design/calculation-workspace.md) adds three stateless endpoints.
`POST /api/calculations/inspect` takes `{project, document}`, where `document` is a version-1 model
or a calculation workspace; it replays the workspace and returns the effective model, the preview
against `project`, the relationship (`bound`, `earlier`, `different`), the chain of bound
revisions, static factor usage, per-formula checks and target changes.
`POST /api/calculations/propose` takes `{project, workspace, event, expected_review_digest}` and
returns the inspected candidate with one appended `unit`, `source`, `formula`, `review`, `remove`
or `rebind` event. `POST /api/calculations/apply` takes `{project, workspace,
expected_review_digest, recorded_by, recorded_at}` and returns the candidate with its `apply`
event, the target assignments (apply them as one `POST /api/edit` batch of `set_performance`
operations) and the version-1 calculation bundle whose compiled fingerprint the edited project
must equal. A changed digest returns 412; a refused event or changed history returns 409 with a
`CALCULATION_*` code in the message; malformed events return 422. Nothing is written.

| Rule | What it means |
| --- | --- |
| **Stateless editing** | The server holds no session. The client owns the unsaved working copy and sends it with each request. `POST /api/edit` applies a list of operations to the project in the body and returns the new project; **nothing is stored**. Undo/redo is the client keeping earlier copies |
| **All-or-nothing edits** | If operation *i* is refused, the response names `operations[i]` and no project is returned |
| **Drafts can be saved** | A semantically incomplete project (missing scale, measurement or rating) is saved as a draft. Only a structurally corrupt one (cycle, unknown parent, duplicate ID) is refused (`MODEL_STRUCTURE`) |
| **Identity** | A project's `id` is fixed at creation and is its file name (`<id>.json`). `PUT /api/projects/{id}` requires the body's `id` to equal the URL's (`ID_MISMATCH`). IDs match `^[A-Za-z0-9][A-Za-z0-9_.\-]{0,63}$`, so an ID can never name a path outside the library |
| **Revisions** | Every project response carries `fingerprint` (also as the `ETag` header): a SHA-256 of the canonical project JSON. The client treats "draft fingerprint ≠ saved fingerprint" as "unsaved changes" |
| **Optimistic concurrency** | `PUT` accepts `If-Match: "<fingerprint>"`. If the stored project is no longer that revision, the answer is `412 STALE_REVISION` and nothing is written. Without the header the write is unconditional |
| **No silent loss** | Delete moves the file to `<library>/.trash/`. Create and import never overwrite. An unreadable project file is listed under `unreadable`, never hidden |
| **Local only** | The server binds `127.0.0.1` by default. `TrustedHostMiddleware` accepts only `localhost`, `127.0.0.1` and `[::1]` (and the test host). **No CORS is enabled**, so a web page on another origin cannot read the API |
| **Validation vs evaluation** | `validate` always answers with a report. `evaluate`, `sensitivity` and the analysis-record routes refuse a model with errors: `422 VALIDATION_FAILED` |
| **Read-only analysis** | Previews, probes, comparisons and records never call the project store and never change an ETag |

## Errors

Every error has this body (`details` may be empty):

```json
{"error": {"code": "STALE_REVISION", "message": "…human-readable…",
           "details": [{"path": "operations[2]", "message": "…"}]}}
```

| HTTP | `code` | When |
| --- | --- | --- |
| 400 | `MCDA_ERROR` | Any other domain error |
| 404 | `PROJECT_NOT_FOUND` | No project with that ID |
| 404 | `EXAMPLE_NOT_FOUND` | No bundled example with that name |
| 404 | `NOT_FOUND` | No such API endpoint (also when a frontend is mounted) |
| 405 | `METHOD_NOT_ALLOWED` | Real path, wrong method; the `Allow` header lists the right ones |
| 409 | `PROJECT_EXISTS` | Create/import of an ID that is already stored |
| 409 | `EDIT_REFUSED` | An operation the services layer refuses (for example a duplicate ID, or adding a child that would discard measured data without `discard_leaf_data`) |
| 412 | `STALE_REVISION` | `If-Match`, or an export's expected fingerprint/digest, does not match |
| 413 | `ANALYSIS_LIMIT` | A results/export request exceeds the workspace bounds |
| 422 | `INVALID_REQUEST` | Body or parameters do not match the schema (`details` have field paths) |
| 422 | `INVALID_PROJECT_ID` | ID is not a legal project ID |
| 422 | `ID_MISMATCH` | Body ID ≠ URL ID |
| 422 | `UNSUPPORTED_SCHEMA_VERSION` | `PUT` body is not schema version 1 |
| 422 | `INVALID_PROJECT_FILE` | Imported JSON is not a valid project (`details` locate the problems) |
| 422 | `UNKNOWN_REFERENCE` | A request or operation names an alternative, criterion, profile, scenario or method that does not exist |
| 422 | `MODEL_STRUCTURE` | Cycle, unknown parent or duplicate ID in the tree |
| 422 | `VALIDATION_FAILED` | Analysis requested on a model that has validation errors |
| 422 | `SENSITIVITY_UNDEFINED` | The node cannot be varied (for example an only child) |
| 422 | `OUT_OF_DOMAIN` | A measurement outside the value function's range under the `error` policy |
| 422 | `INVALID_WEIGHTS` | Weights cannot be derived |
| 422 | `EXPORT_UNAVAILABLE` | Unknown visibility IDs, a comparison export that is not available, or a CSV table the method does not declare (for example `classes` for MAVT) |
| 422 | `METHOD_NOT_SUPPORTED` | The configured method does not offer what the request needs: a capability (sensitivity, probes, scenario comparison, previews), an analysis record or export (version 1 for MAVT, version 2 for methods that have one), or an API result model. One `details` entry names `method`, the `requirement` and the method's declared `capabilities`. An unregistered method is not refused here; it fails validation with `UNKNOWN_METHOD` |
| 500 | `STORED_PROJECT_UNREADABLE` | The stored file exists but cannot be read |

The generated OpenAPI document declares only FastAPI's `422` for most endpoints. This table is the
complete list of runtime errors.

Evaluate, sensitivity and compare are **bit-identical** to calling the engine directly and to the
CLI's `--json` output. Tests assert equality, not closeness. An MAVT body is unchanged by the
unions: it carries no sorting field, and the sensitivity bodies of MAVT carry no `method`.

`GET /api/meta` lists each registered method's `name`, `label`, `capabilities` and
`export_tables` (the CSV tables its record can fill).

**The shared `ranking`.** Every result has `ranking`, a best-first list of
`{alternative_id, name, value, rank}` with competition ranks. Its `value` is the method's ranking
quantity: the overall MAVT value for MAVT and sorting, MAVT's reference value for SMAA-2, and the overall
AHP priority (a share of the goal) for AHP. For
**PROMETHEE II it is the net outranking flow**, in [−1, 1], not a preference value; the result's
`flows` holds the same number as `net_flow` with the positive and negative flows, and no
PROMETHEE II view, CSV table or CLI line shows it under the word "value". A `PrometheeResult` also
has the single-criterion flows, the preference matrix, the PROMETHEE I `partial_order` and the
`explanation` against MAVT, whose `weight_profile_id` and `scenario_id` are the result's.

## Edit operations

Each operation is an object with an `op` discriminator. They map one-to-one onto
`services/project_service` functions; a test applies each through the API and through the service
and requires identical projects. `?` marks an optional field.

**Project, alternatives and criteria**

| `op` | Fields |
| --- | --- |
| `update_project` | `title?`, `description?`, `decision_maker?` |
| `add_alternative` | `name`, `alternative_id?` |
| `rename_alternative` | `alternative_id`, `name` |
| `remove_alternative` | `alternative_id` (its measurements go with it) |
| `add_criterion` | `name`, `parent_id?`, `position?`, `criterion_id?`, `scale?`, `value_function?`, `discard_leaf_data?` |
| `update_criterion` | `criterion_id`, `name?`, `description?` (the ID never changes) |
| `move_criterion` | `criterion_id`, `new_parent_id?`, `position?`, `discard_leaf_data?` |
| `remove_criterion` | `criterion_id` (its sub-tree, measurements and ratings go with it) |
| `set_scale` | `criterion_id`, `scale` |
| `set_value_function` | `criterion_id`, `value_function` |
| `set_performance` | `alternative_id`, `criterion_id`, `value` (a number, or a label for labelled scales) |
| `clear_performance` | `alternative_id`, `criterion_id` (idempotent) |
| `clear_criterion_performances` | `criterion_id` |

Making a measured leaf into a group discards its scale, value function and measurements. This
happens when you add a child to it or move something under it. The services layer refuses that
unless `discard_leaf_data` is true, so a client has to ask the user first; the application does.

**Weights and profiles**

| `op` | Fields |
| --- | --- |
| `set_judgement` | `node_id`, `rating`, `profile_id?` (default: the first profile) |
| `clear_judgement` | `node_id`, `profile_id?` (idempotent) |
| `create_weight_profile` | `name`, `profile_id?` (a new profile starts with no ratings) |
| `duplicate_weight_profile` | `profile_id`, `name`, `new_profile_id?` (deep copy; independent afterwards) |
| `rename_weight_profile` | `profile_id`, `name` (the ID never changes) |
| `remove_weight_profile` | `profile_id`, `replacement_profile_id?` (required when referenced) |
| `set_default_weight_profile` | `profile_id` (`null` restores automatic resolution) |

Raw swing ratings are the only weight input. No operation writes a local or global weight,
because those are always derived.

**Profile reference integrity:**

- **The last profile** cannot be removed.
- **Referenced profiles.** `remove_weight_profile` refuses a profile that a scenario or the saved
  analysis resolves to, including an *automatic* first-profile reference, unless
  `replacement_profile_id` names a different existing profile. It then rewrites every affected
  reference in the same immutable edit. No dangling ID can be produced, and nothing silently falls
  back to another profile.
- **Errors.** Refusals are `409 EDIT_REFUSED` with the offending reference paths. Unknown IDs are
  `422 UNKNOWN_REFERENCE`.
- **Defaults versus viewing.** `set_default_weight_profile` changes only
  `analysis.weight_profile_id`. Selecting a profile for viewing is client-side state and sends no
  operation.

**Scenarios**

| `op` | Fields |
| --- | --- |
| `create_scenario` | `name`, `scenario_id?` |
| `duplicate_scenario` | `scenario_id`, `name`, `new_scenario_id?` |
| `rename_scenario` | `scenario_id`, `name` |
| `remove_scenario` | `scenario_id`, `repair_default` (default `false`), `replacement_scenario_id?` (nullable) |
| `set_scenario_profile` | `scenario_id`, `profile_id` (required, nullable) |
| `set_scenario_override` | `scenario_id`, `criterion_id`, `value_function` |
| `clear_scenario_override` | `scenario_id`, `criterion_id` |
| `set_default_scenario` | `scenario_id` (required, nullable) |

**IDs and copies.**

- **Stable IDs.** IDs are generated deterministically from names, with suffixes on collision, when
  not supplied.
- **Duplicates** copy the profile reference and sparse overrides into independent data.

**What is refused.**

- **Bad overrides.** Unknown references, overrides on objectives, and incompatible definitions are
  refused.
- **Missing local measurements** may stay incomplete, but they are never fabricated.

**Deleting the saved-default scenario.**

- **Repair is required:** `repair_default: true`, optionally with a different
  `replacement_scenario_id`.
- **`null` repairs to Base.**
- **Without repair** the deletion is refused.

Failures leave the entire draft unchanged.

**Value-based sorting and the saved method**

| `op` | Fields |
| --- | --- |
| `set_sorting_model` | `sorting` (the whole section: `classes[]`, `audit?`); its rules are validation issues, so a draft may be applied incomplete |
| `clear_sorting_model` | none; the project returns to schema version 1 when it has no other version-2 section |
| `set_smaa_model` | `smaa` (the whole section: `dependence`, `cells[]`, `groups[]`, `shared_draws[]`); its rules are validation issues |
| `clear_smaa_model` | none; the project returns to the lowest schema version it needs |
| `set_promethee_model` | `promethee` (the whole section: `criteria[]`, each with `criterion_id`, `direction`, `weight`, `function` and, on a labelled leaf, `coding`); its rules are validation issues |
| `clear_promethee_model` | none; the project returns to the lowest schema version it needs |
| `set_ahp_model` | `ahp` (the whole section: `criteria[]` by `parent_id` and `alternatives[]` by `criterion_id`, each with `judgements[]` of `{row, column, value}`); its rules are validation issues |
| `clear_ahp_model` | none; the project returns to the lowest schema version it needs |
| `set_requirements` | `requirements` (the whole list of `bound` and `labels` requirements); an empty list removes the section. Its rules are validation issues of the feasibility check |
| `clear_requirements` | none; the project returns to the lowest schema version it needs |
| `set_analysis_method` | `method` (registered); changing it also clears `analysis.parameters`, which belonged to the previous method |

`remove_alternative` and `remove_criterion` also remove the stated uncertainty of what they remove,
as they remove its measurements; `remove_criterion` also removes its PROMETHEE entry, and both
remove the AHP judgements that name what they remove; `remove_criterion` also removes the
requirements on the leaves it removes.

Viewing another method is client-side state and sends no operation, like viewing a profile or
scenario.

## Previews

Behaviour is described in [previews](../design/previews.md).

**Value-function preview.** Request: `{project, criterion_id, configuration?, candidate?,
sample_count?}`.

- **Candidate fields:** `{scale?, value_function?}`. Omitted means inherit; `null` means clear in
  the preview only. `sample_count` is 2–501.
- **Readiness:** two independent enums, `readiness` for the function and `measurement_readiness`
  for its relevant readings, each `ready | incomplete | invalid`. The booleans `curve_ready` and
  `measurements_complete` remain.
- **What readiness depends on:** fixed-domain readiness ignores weights and unrelated readings.
  Local linear curves need every relevant alternative's valid reading.

**Weight preview.** Request: `{project, configuration?}`. If `weights_ready` is false, the
local/global weight maps are empty. Two fields explain weights:

- `swing_ranges` maps every **leaf** ID to the context for its worst-to-best swing:
  - `readiness`, `scale_type`, `unit` and `domain`;
  - the resolved `worst`/`best` measurements;
  - its own `diagnostics`.

  Endpoints follow the value function, so a decreasing criterion reports its highest number as
  *worst*. A labelled scale reports labels, not codes. Range readiness is independent of the
  weights.
- `path_shares` maps **every** node ID, objectives included, to the product of local weights along
  its root path. A leaf's share equals its global weight. A group's shares sum to its parent's
  share. It is empty when `weights_ready` is false, and it exists so a client never has to multiply
  weights itself.

**Common to both previews.**

- **Provenance.** Both responses carry the snapshot fingerprint, the complete configuration and the
  resolved profile and scenario.
- **Incomplete models** return 200 with diagnostics and readiness flags. Missing measurements,
  anchors or weights are never guessed.
- **Diagnostics, not errors.** `SWING_RANGE_REVIEW`, `PREVIEW_SAMPLE_LIMIT` and `NO_WEIGHT_PROFILE`
  are diagnostics, not HTTP error codes.

## Sensitivity probe

```
POST /api/sensitivity/probe                 {project, node_id, weight, configuration?}
POST /api/projects/{id}/sensitivity/probe   {node_id, weight, configuration?}
```

**What `weight` is.** A hypothetical **local** weight for `node_id`, finite and within [0, 1]. It
is checked by the schema (422) and again in the engine. It is a what-if setting, **not** a swing
judgement, a saved profile or an edit. The response's `project_fingerprint` is the fingerprint of
the project that was sent, unchanged.

The response carries the provenance envelope (`project_fingerprint`, `configuration`,
`weight_profile_id`, `scenario_id`) plus:

| Field | Meaning |
| --- | --- |
| `node_id`, `node_name`, `node_path` | The varied criterion and its root path |
| `weight`, `base_weight` | The probed weight, echoed, and its weight in the unmodified model |
| `local_weights` | The affected sibling group after proportional redistribution |
| `global_weights`, `path_shares` | Hypothetical leaf weights and branch shares, engine-derived |
| `alternatives` | Best first: value, **competition rank**, baseline value and baseline rank |
| `ranking`, `baseline_ranking` | IDs, with ties in the project's own alternative order |
| `ranking_differs_from_baseline` | Competition-rank maps differ, including a tie forming or dissolving |
| `winner_differs_from_baseline` | Rank-one winner ID sets differ. A swap below the leader is not a winner change |
| `diagnostics` | `TIED_ALTERNATIVES`, `PROBE_AT_BASELINE` |

**Ranks.** Ranks are competition ranks from the engine: a tie at a crossover reads `1, 1, 3`,
never `1, 2, 3`. A client must not derive ranks from array positions.

**Redistribution.** It reuses the sweep's implementation, including its summed denominator. The
denominator is not `1 − w_k`, which cancels catastrophically near 1. Eligibility is shared with the
sweep, so the two never disagree. These are refused with `422` and a reason:

- a node with no siblings;
- a node already at local weight 1;
- an unknown criterion or profile.

**Numerical note.** The probe sums with `math.fsum`, like evaluation, so a probe at the baseline
weight equals the Results value bit for bit. The sweep's grid uses a NumPy matmul and can differ in
the last bit; at most 1.11e-16 was measured on the VC example. Use the probe for any number shown
as text. See [sensitivity](../design/sensitivity.md).

## Scenarios and scoped validation

`POST /api/analysis/validate` returns the provenance envelope plus `validation`, a report for the
effective selected model.

- **What it checks:** only the selected profile and the resolved functions, plus the global
  structural checks.
- **Full report:** `POST /api/validate` still gives the full-project report.
- **Unknown IDs** fail explicitly and never trigger a fallback.

**Scenario comparison.** Request shapes are unchanged. Responses add:

- at the root: `project_fingerprint`, `configuration` and `scenario_ids`;
- per outcome: `configuration`, `weight_profile_id`, `applied_overrides`, `resolved_domains`,
  `diagnostics` and `delta_from_baseline`.

**How comparison is computed.**

- **Baseline:** clears only `scenario_id`; an explicit profile remains.
- **Profiles:** each selected scenario resolves explicit profile → scenario profile → first profile.
- **What changed:** the winner change compares rank-one ID sets, and the ranking change compares
  rank maps, including ties.
- **Invalid scenarios** fail rather than falling back.
- **Read-only:** comparison saves nothing and uses the same summation path as Results.

See [scenarios](../design/scenarios.md).

## Analysis records and downloads

| Route | Request | Response |
| --- | --- | --- |
| `POST /api/analysis/record` | `{project, configuration?}` | `AnalysisRecord`, `SortingAnalysisRecord` or `SmaaAnalysisRecord` |
| `POST /api/projects/{id}/analysis/record` | `{configuration?}` | `AnalysisRecord`, `SortingAnalysisRecord` or `SmaaAnalysisRecord` |
| `POST /api/analysis/export` | Export options plus `project` | JSON or CSV attachment |
| `POST /api/projects/{id}/analysis/export` | Export options | JSON or CSV attachment |

**What a record contains.** `AnalysisRecord` wraps the unchanged `MavtResult` with:

- record version and digest;
- context labels;
- criterion definitions, paths, scales and domains;
- authoritative path shares and contribution totals;
- dominance relation descriptions;
- the selected-scenario comparison, or a diagnostic explaining why it is unavailable.

The digest is the SHA-256 of canonical, sorted, compact UTF-8 record JSON, excluding
`record_digest`. Records contain no timestamps, sampled sensitivity values or persisted chart
fields.

**Version 2.** Every method but MAVT has a version-2 record: a common envelope
(`record_version: "2"`, digest, `method`, `method_label`, `calculation_path`, tolerance, CSV text
policy, project title, scenario and profile names, alternative order, configuration) plus the
method's result and context. `SortingAnalysisRecord` holds `MavtSortingResult` (calculation path
`mavt_sorting.math_fsum.v1`) and the same value-model context as version 1, because sorting
declares `contributions`. The digest rule is the same. Version-1 records are unchanged and remain
MAVT only; a JSON export of a version-2 record has `export_version: "2"`.
`SmaaAnalysisRecord` holds `SmaaResult` (calculation path `smaa2.pcg64.v1`) with its full
provenance (run, draws or exact outcomes, seed, confidence, the stated uncertainty, environment)
and no MAVT value context. Its result, tables and charts carry the label "sampled acceptability
under these assumptions".
`PrometheeAnalysisRecord` holds `PrometheeResult` (calculation path `promethee2.v1`) and no MAVT
value context; the MAVT side of its explanation is inside the result. Its result, tables and
charts carry the label "net outranking flows: these compare the alternatives with one another and
are not preference values".
`AhpAnalysisRecord` holds `AhpResult` (calculation path `ahp.eigen_power.v1`): every matrix with its
priorities and consistency, criterion and alternative priorities, the synthesis mode and the
random-index table. AHP reads no profile or scenario, so its result names neither (`null`) and its
record's scenario and profile names are empty. Its result, tables and charts carry the label "AHP
priorities under these pairwise judgements: shares of the goal that sum to one, not MAVT values or
swing weights". A matrix that does not converge is `422 AHP_NO_CONVERGENCE`.

**Export options.**

- **Required:** `expected_project_fingerprint` and `expected_record_digest`, each 64-character
  lowercase hex.
- **Optional:**
  - `configuration`;
  - `format`: `json` or `csv`;
  - `table`: one the method declares in `/api/meta` — MAVT: `ranking`, `contributions`,
    `partial_values`, `dominance`, `comparison`; sorting adds `classes`, and its `ranking` table
    adds `class_id`, `class_name`, `class_rank`, `on_boundary`, `nearest_boundary_class_id`,
    `distance_to_nearest_boundary` and `in_audit_sample`; SMAA-2 offers `rank_acceptability`
    (per alternative, every rank, then sole and tied first, with count, frequency and interval),
    `class_acceptability` (refused when the run has no classes) and `inputs_to_check`;
    PROMETHEE II offers `flows` (positive, negative and net flow and rank), `criterion_flows`
    (per alternative and leaf, with the inputs used), `partial_order` (every pair's PROMETHEE I
    relation) and `explanation` (one row per criterion of each detailed pair, one row per other
    pair; refused when the explanation is unavailable), every row with a `label` column;
    AHP offers `priorities` (rank, priority and ideal score), `criterion_priorities` (local and
    global), `local_priorities` (per alternative and leaf, with the weighted part) and
    `consistency` (per matrix: λmax, CI, RI, CR, flag and triad), every row with a `label` column;
  - `presentation`: rank or project order, hidden alternative/criterion IDs, display precision.
- **Errors:** a context mismatch is `412 STALE_REVISION`. An invalid selected model fails
  validation instead of producing an exportable result.

**Download response.**

- **Headers:** `Content-Disposition: attachment`, `Cache-Control: no-store`,
  `X-Analysis-Record-Digest` and `X-Project-Fingerprint`.
- **MIME types:** `application/json` and `text/csv; charset=utf-8`.
- **Filenames** use validated IDs and revision prefixes, never untrusted names.
- **JSON** contains the export version, the record, the unchanged source project and the
  presentation settings.
- **CSV** contains complete numerical data and provenance, in deterministic order and at full
  precision.
- **Visibility settings never change the numbers.** CSV text uses the `text-prefix-controls-v1`
  policy (see [results and exports](../design/results-and-exports.md)).

**Draft versus stored routes.** Stored routes compare against the stored revision. Draft routes
analyse the captured snapshot without saving it. The client also verifies the download headers and
suppresses late completions after context changes.

**SVG.** SVG export serialises the rendered chart with provenance and filter metadata in the
browser. It is not a server endpoint.

## Known limits

- **Cooperating processes are coordinated on scoped macOS/Linux local libraries.** The server
  holds lifetime OS ownership; managed-directory CLI writes and store mutations use the same lock.
  Within that server, RLock and If-Match still protect project edits. External/uncooperative programs
  can bypass advisory locking; see [operating limits](../development/library-recovery.md).
- **No authentication.** The API is for the local user only (loopback, no CORS). Do not expose it
  on a network.
- **Incomplete OpenAPI errors.** The OpenAPI document does not enumerate the non-422 error
  responses; see [Errors](#errors).

### Distribution build identity

`GET /api/health` includes `build`: `source_revision`, `source_dirty` and
`frontend_index_sha256`. Bundled releases retain their source revision/dirty flag through an
sdist rebuild. The frontend hash identifies the index actually served, including an override;
it is not a project fingerprint or analysis-record digest. Source/editable installs without a
release manifest report null source identity. `mcda --version` reports the installed package
version and bundled identity without importing optional API dependencies. No project schema or
numerical result contract changes for this addition.

### C1 library ownership and recovery

The server owns a POSIX advisory library lock for its lifetime. A second cooperating writer/server
is refused with PID/port diagnostics. Project-level If-Match conflicts remain enforced within the
owning server. External programs can bypass advisory locks; see
[coordination and manual recovery](../development/library-recovery.md).

`GET /api/trash` returns entries with `entry`, `project_id`, `title`, `deleted_at`, `readable`,
`conflict` and `error`. Unsafe/unreadable entries remain visible. `POST /api/trash/{entry}/restore`
accepts `{ "as_copy": false }` or true and returns the ordinary ProjectDocument with Location/ETag.
Both successful modes retain the recovery entry. Original-ID conflicts return 409 PROJECT_EXISTS;
copy creates a new ID/fingerprint. Traversal/symlink/ID validation and publication failures use
the normal error envelope; no project schema or numerical result contract changes.

## Open Questions (partial)

`POST /api/open-questions` accepts a draft project and optional analysis configuration. It returns
the project fingerprint, configuration, grouped questions, coverage and limitations. The current
slice assesses missing measurements, unknown requirements, one-way MAVT winner-change weights,
class-change weights, SMAA-2 inputs-to-check heuristics and leader disagreements between methods;
it explicitly reports when weight sensitivity cannot run. An optional `dossier` adds evidence
questions when its fingerprint and references validate. The route is read-only.


## Fundamental-factor uncertainty runs

These are separate sidecar runs, not a change to `/evaluate` or to cell-based SMAA-2. Existing
project/result schemas and outputs remain unchanged. See the generated OpenAPI for complete bodies.

| Endpoint | Read-only behavior |
| --- | --- |
| `POST /api/factor-uncertainty/inspect` | Project, calculation model and factor sidecar → typed sidecar, validation issues and dependency/source-assumption questions; pending reviews remain pending |
| `POST /api/factor-uncertainty/run` | Bound inputs and explicit run/evaluation/seed/draw count/configuration → sealed version-1 run with deterministic reference, acceptabilities, trace and reproducibility metadata; optional decision details retain a version-2 deterministic snapshot beside it |
| `POST /api/factor-uncertainty/verify` | Retained record and optional `replay` → verified historical record; no automatic rebinding or replay |

The run types are `mavt`, `mavt_sorting` and `smaa2_factors`; evaluation is `sampled` or
`exact_enumeration`. Fixed weights only, no additional cell/weight uncertainty. Derived-target
cell uncertainty is a double specification and is refused by the calculation gate. An invalid
draw aborts with HTTP 422 `INVALID_FACTOR_DRAW`, including `draw`, `formula_id` and `factor_ids`
in details. Invalid input/supports use the normal validation envelope. Malformed/changed retained
records use `EDIT_REFUSED`. Ordinary source project/library files are never changed.

`POST /api/open-questions` optionally accepts a local `factor_record`. Its binding/integrity is
verified before adding factor questions; stale/invalid records contribute an unavailable reason,
never rebound questions. Omission preserves the earlier response exactly.
